# botfactory — бот, который делает ботов

Пишете в Telegram «сделай бота для магазина, название Магазин у дома» — в
ответ приходит ссылка на репозиторий, в котором уже лежит работающий бот с
тестами, Docker и CI.

```
Вы:  сделай бота для магазина, название «Магазин у дома», публичный

Бот: Заказ №7
     Пакет: shop
     Название: Магазин у дома
     Репозиторий: shop-bot
     Куда: новый репозиторий
     Видимость: публичный
     [🚀 Собрать] [→ ветка] [→ приватный] [Отмена]

Бот: Готово: Магазин у дома
     https://github.com/seller/shop-bot
     В коммите 24 файла.
```

Под капотом — [`botkit`](../botkit/): генератор проекта и публикация в GitHub.
Фабрика добавляет к ним разбор заказа словами, карточку с кнопками и историю
сборок.

## Запуск

```bash
cp .env.example .env      # BOT_TOKEN, OWNER_ID, GITHUB_TOKEN
docker compose up -d --build
```

Без Docker:

```bash
pip install -e ../botkit
pip install -e ".[dev]"
python -m botfactory run
```

`GITHUB_TOKEN` — personal access token с правом создавать репозитории:
classic со scope `repo` или fine-grained с `Administration: Read and write` и
`Contents: Read and write`.

## Два режима публикации

| `PUBLISH_MODE` | Что делает | Когда нужен |
| --- | --- | --- |
| `repo` | создаёт отдельный репозиторий и пушит туда проект вместе с копией botkit в `vendor/` | бот для заказчика, живёт своей жизнью |
| `branch` | коммитит подкаталог веткой `bot/<имя>` в репозиторий из `REPO_ROOT` | новый бот в общий репозиторий, дальше — pull request |

Режим выбирается в `.env`, называется словами в заказе («веткой», «отдельным
репозиторием») и переключается кнопкой под карточкой — до сборки.

Для `branch` нужен рабочий клон с настроенным `origin`; путь к нему —
`REPO_ROOT`. Публикация останавливается, если в этом клоне есть
незакоммиченные изменения вне каталога бота: иначе чужие правки уехали бы в
чужую ветку.

## Что понимает из фразы

| Пишете | Получаете |
| --- | --- |
| `бота shop` | пакет `shop` |
| `бота для магазина`, `для записи`, `для отзывов` | `shop`, `booking`, `reviews` — по словарю типовых ботов |
| `бота теплица` | `teplica` — транслитерация, если слово незнакомое |
| `«Магазин у дома»` или `название Магазин у дома` | название в README и приветствии |
| `публичный` / `приватный` | видимость репозитория |
| `веткой` / `отдельным репозиторием` | режим публикации |
| `репозиторий my-shop-bot` | имя репозитория |

Непонятое не додумывается: бот показывает карточку с тем, что разобрал, и
ждёт подтверждения. Всё, что разобрано неверно, правится кнопками.

## Команды

| Команда | Что делает |
| --- | --- |
| `/help` | как заказать бота |
| `/builds` | последние сборки со ссылками и ошибками |
| `/stats` | сколько собрано, сколько сломалось |

Из консоли — тот же путь без Telegram, чтобы проверить токен и права:

```bash
python -m botfactory make бота для магазина, название "Магазин у дома"
python -m botfactory builds
```

## Кто может заказывать

Только `OWNER_ID` и `ADMIN_IDS`. Это не перестраховка: бот создаёт
репозитории под вашим токеном, и любой, кто до него дотянется, будет делать
это от вашего имени. Посторонним бот отвечает отказом.

## Репозиторий заказчика собирается сам по себе

В режиме `repo` botkit кладётся внутрь проекта, в `vendor/botkit`, а
Dockerfile и compose собираются из корня репозитория. Иначе получатель, у
которого botkit рядом не лежит, упирался бы в `COPY botkit /app/botkit` и
`ModuleNotFoundError: No module named 'botkit'` — каркас не опубликован в
PyPI и ставится только из исходников.

В режиме `branch` копии нет: в общем репозитории botkit уже есть, дублировать
его там незачем.

## Что учтено

- **Двойное нажатие «Собрать».** Статус меняется одним `UPDATE ... WHERE
  status = 'new'`: вторая сборка и второй пуш в тот же репозиторий не
  запускаются.
- **Токен не оседает в `.git/config`.** Он подставляется в адрес одного
  `git push` и вырезается из текста ошибок.
- **Перезапуск во время сборки.** Зависшие сборки помечаются неудачными при
  старте — «собирается» навсегда хуже, чем честная ошибка с кнопкой
  «Повторить».
- **Имя репозитория из русского названия.** «Магазин у дома» →
  `magazin-u-doma`, а не вереница дефисов, которую GitHub сделал бы молча.
- **Занятое имя.** Проверяется до генерации: понятное «репозиторий уже есть,
  вот ссылка» полезнее, чем ошибка 422 после.
- **Сборка у заказчика.** CI ставит сгенерированный автономный проект в
  чистое окружение и гоняет его тесты: «у меня работает» здесь не считается
  проверкой.

## Тесты

```bash
pytest -q
ruff check src tests
```

Сети в тестах нет: роль GitHub играет локальный bare-репозиторий, роль API —
заглушка. Проверяется то, ради чего бот написан: после заказа код
действительно оказывается в репозитории, а чужие изменения — нет.

## Чего здесь нет

- **Правок готового бота.** Фабрика создаёт проект из шаблона; дальше его
  правят руками. Генерировать по описанию произвольную логику — другая
  задача и другой инструмент.
- **Очереди.** Сборка занимает секунды, заказы идут по одному от владельца;
  очередь усложнила бы код, ничего не дав.
- **Своего деплоя.** Сгенерированный бот приезжает с `docker-compose.yml` —
  запускать его на сервере фабрика не пытается.
